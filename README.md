# bulk-psi-crux-report

گزارش سرعت صفحات در یک فایل اکسل.

**PageSpeed به‌صورت پیش‌فرض اجرا می‌شود** — چون روی هر URL کار می‌کند، چه ترافیک داشته باشد چه نه.

**CrUX اختیاری است** و با `--crux origin` روشن می‌شود: یک کال به‌ازای هر دامنه×دستگاه، که تنها اندازه‌گیری کاربر واقعیِ سایت را می‌دهد به‌علاوه‌ی تاریخچه‌ی هفتگی — چیزی که PageSpeed ذاتاً نمی‌تواند بدهد، چون هر اجرایش یک عکس فوری است.

> **خروجی کنسول انگلیسی است.** ترمینال ویندوز متن راست‌به‌چپ را حرف‌به‌حرف و برعکس نشان می‌دهد، پس فارسی آنجا ناخوانا می‌شد. راهنمای فارسی همین فایل است.

## راه‌اندازی

```bash
npm install
```

بعد یک فایل `.env` بساز:

```
CRUX_API_KEY=AIza...
```

کلید را از Google Cloud بگیر: یک پروژه بساز، **Chrome UX Report API** و **PageSpeed Insights API** را Enable کن، بعد از **Credentials → Create credentials → API key** یک کلید بساز.

> در بخش **Application restrictions** گزینه‌ی `None` را نگه دار. اگر روی «HTTP referrers» یا «IP addresses» بگذاری، کالِ سرور‌به‌سرور رد می‌شود. محدودیت واقعی را در **API restrictions** بگذار و همان دو API را تیک بزن.

## سه حالت ورودی

```bash
node index.js --file urls.txt --max 20
```

فایل متنی، هر خط یک URL. خط خالی و خطی که با `#` شروع شود نادیده گرفته می‌شود. اگر دامنه بدون `https://` بنویسی خودش اضافه می‌کند.

```bash
node index.js --sitemap https://example.com/post-sitemap.xml --filter /blog/
```

یک sitemap مسطح.

```bash
node index.js --sitemap-index https://example.com/sitemap_index.xml
```

sitemap فرزندان را با تعداد URL هرکدام لیست می‌کند و می‌پرسد کدام‌ها را می‌خواهی — `1,3` یا `2-4` یا `a` برای همه. هر sitemap انتخاب‌شده یک شیت جدا می‌گیرد.

برای اجرای زمان‌بندی‌شده، `--pick 1,3` پرسش را رد می‌کند.

## دستورهای آماده

نُه حالتی که واقعاً پیش می‌آیند. زمان‌ها با پیش‌فرض `--psi-concurrency 10` حساب شده‌اند.

### ۱. چک سریع قبل از تحویل سایت

```bash
node index.js --file urls.txt --devices mobile
```

چند صفحه‌ی مهم را در `urls.txt` بریز (هر خط یک URL — قالبش در `urls.example.txt` هست) و فقط موبایل را بگیر. گوگل هم موبایل را ملاک رتبه می‌گیرد، پس دسکتاپ در این مرحله فقط زمان می‌خورد. ۵ صفحه ≈ نیم دقیقه.

### ۲. کل سایت وردپرسی، یک‌جا

```bash
node index.js --sitemap-index https://example.com/sitemap_index.xml --pick all --max all --devices mobile
```

`--pick all` یعنی همه‌ی sitemapها بدون پرسش، `--max all` یعنی سقف ۵۰تایی برداشته شود. هر sitemap یک شیت می‌گیرد و یک شیت `All` هم همه را با هم مرتب می‌کند.

**قبل از اجرا حواست به عدد باشد.** ابزار قبل از شروع تعداد کال و تخمین زمان را چاپ می‌کند؛ ۴۰۰ صفحه یعنی حدود ۳۶ دقیقه.

### ۳. فقط یک بخش از سایت

```bash
node index.js --sitemap-index https://example.com/sitemap_index.xml --pick all --max all --filter /blog/
```

`--filter` روی همه‌ی گروه‌ها اعمال می‌شود، پس لازم نیست بدانی مقاله‌ها در کدام sitemap هستند. اگر الگو پیچیده‌تر است، regex بده: `--filter "/\/(blog|news)\//"`.

### ۴. گزارش ماهانه‌ی مشتری، با داده‌ی کاربر واقعی

```bash
node index.js --sitemap-index https://example.com/sitemap_index.xml --pick all --max all --crux origin
```

این تنها حالتی است که شیت **Trend** ساخته می‌شود: روند هفتگی LCP و INP و CLS از داده‌ی کاربران واقعی. کل هزینه‌اش ۴ کال اضافه است (دامنه × دستگاه × جاری/تاریخچه) و چیزی می‌دهد که PageSpeed ذاتاً نمی‌تواند — اینکه سایت **در طول زمان** بهتر شده یا بدتر.

برای گزارش مشتری بگذار هر دو دستگاه بماند؛ فقط بدان تعداد کال PageSpeed دو برابر می‌شود.

### ۵. سایت پرترافیک، داده‌ی میدانی تک‌تک صفحات

```bash
node index.js --sitemap https://example.com/post-sitemap.xml --max all --crux pages --psi failed
```

`--crux pages` برای هر URL جدا داده‌ی کاربر واقعی می‌گیرد، و `--psi failed` باعث می‌شود PageSpeed فقط روی صفحاتی اجرا شود که در داده‌ی میدانی مردود شده‌اند. روی یک سایت پرترافیک این هم دقیق‌ترین و هم کم‌هزینه‌ترین ترکیب است.

**ولی اگر سایتت ترافیک بالایی ندارد این را اجرا نکن** — تک‌تک صفحات `NO DATA` برمی‌گردانند، بعد `--psi failed` هیچ صفحه‌ای برای تست پیدا نمی‌کند و گزارش عملاً خالی درمی‌آید. مورد ۴ را بگیر.

### ۶. اجرای زمان‌بندی‌شده

```bash
node index.js --sitemap-index https://example.com/sitemap_index.xml --pick all --max all --devices mobile --quiet --out reports/weekly.xlsx
```

`--pick` پرسش تعاملی را حذف می‌کند و `--quiet` فقط خطاها را چاپ می‌کند — دو چیزی که یک اجرای خودکار به آن نیاز دارد. با `--out` مسیر ثابت بده، وگرنه هر بار یک فایل با تاریخ جدید ساخته می‌شود.

در Task Scheduler ویندوز، Start in را روی پوشه‌ی پروژه بگذار تا `.env` پیدا شود.

### ۷. وقتی عجله داری

```bash
node index.js --sitemap-index https://example.com/sitemap_index.xml --pick all --max all --devices mobile --psi-concurrency 20
```

`--devices mobile` تعداد کال را **نصف** می‌کند و هیچ عارضه‌ای ندارد. `--psi-concurrency 20` سرعت را حدود ۱٫۴ برابر می‌کند. بالاتر از ۲۰ نرو — دلیلش در بخش آخر همین فایل توضیح داده شده و ابزار هم خودش هشدار می‌دهد.

### ۸. سایت چندزبانه

```bash
node index.js --sitemap https://example.com/sitemap.xml --max 50 --filter "/^(?!.*[?&]hl=).*$/"
```

sitemapهای چندزبانه معمولاً با نسخه‌های زبانی صفحه‌ی اول شروع می‌شوند، پس ۵۰ URL اولی که `--max` برمی‌دارد می‌تواند همگی یک صفحه باشد. این فیلتر پارامتر `hl=` را کنار می‌گذارد.

### ۹. فقط یک صفحه، برای بررسی نوسان

```bash
node index.js --file one-url.txt --devices mobile
```

همین را چند بار پشت‌سرهم بگیر. اگر نمره بین دو اجرا ۲۰ واحد فرق کرد باگ نیست — نوسان واقعی PageSpeed است و خودش یک یافته است: یعنی صفحه یک منبع ناپایدار دارد.

## گزینه‌ها

| فلگ | کار |
| --- | --- |
| `--max <n\|all>` | سقف URL در هر گروه (پیش‌فرض ۵۰؛ `all` یعنی بدون سقف) |
| `--filter <s>` | زیررشته یا `/regex/` — فقط URLهای منطبق |
| `--devices <list>` | `mobile` یا `desktop` یا هر دو (پیش‌فرض هر دو) |
| `--crux <scope>` | `none` \| `origin` \| `pages` (پیش‌فرض `none`) |
| `--no-trend` | شیت روند ساخته نشود |
| `--trend-weeks <n>` | تعداد هفته‌های تاریخچه، ۱ تا ۴۰ (پیش‌فرض ۲۵) |
| `--no-origin-fallback` | اگر صفحه‌ای داده نداشت، سراغ سطح دامنه نرو |
| `--psi <scope>` | `none` \| `failed` \| `all` (پیش‌فرض `all`) |
| `--out <file>` | مسیر خروجی؛ پیش‌فرض `pagespeed-<سایت>-<تاریخ>.xlsx` یا `speed-...` اگر CrUX هم اجرا شود |
| `--concurrency <n>` | تعداد درخواست هم‌زمان CrUX (پیش‌فرض ۸) |
| `--psi-concurrency <n>` | تعداد درخواست هم‌زمان PageSpeed (پیش‌فرض ۱۰) |
| `--quiet` | فقط خطاها |

**فلگ اشتباه، اجرا را متوقف می‌کند.** اگر پارامتری را غلط بنویسی یا پارامتری که مقدار می‌خواهد را بدون مقدار بدهی، ابزار خطا می‌دهد و نزدیک‌ترین فلگ درست را پیشنهاد می‌کند:

```
Unknown flag:
  --device   did you mean --devices ?
Run --help to see every option.
```

این عمدی است. قبلاً فلگ ناشناخته بی‌صدا نادیده گرفته می‌شد و اجرا با پیش‌فرض ادامه پیدا می‌کرد — یعنی گزارشی می‌گرفتی که سالم به نظر می‌رسید ولی به سؤال دیگری جواب داده بود.

## فیلتر URL — این را جدی بگیر

sitemapهای واقعی معمولاً هزاران URL دارند و `--max` فقط **N تای اول** را برمی‌دارد. اگر sitemap با نسخه‌های زبانی یک صفحه شروع شود، آن N تا همگی یک صفحه‌ی تکراری‌اند.

روی `developer.chrome.com` تست شد: از ۱۰ URL اول، ۹ تا فقط `?hl=xx` همان صفحه بودند. با این فیلتر درست شد:

```bash
--filter "/^(?!.*[?&]hl=).*$/"
```

## سه حالت `--crux`

| مقدار | چه می‌کند | هزینه |
| --- | --- | --- |
| `none` (پیش‌فرض) | اصلاً CrUX نپرس، فقط PageSpeed | صفر |
| `origin` | یک کال به‌ازای هر دامنه×دستگاه + همان برای تاریخچه | ۴ کال برای یک سایت |
| `pages` | هر URL جدا، با fallback به دامنه اگر داده نداشت | ۲ تا ۴ کال به‌ازای هر URL |

`pages` فقط وقتی می‌ارزد که صفحاتت واقعاً ترافیک بالایی دارند. برای یک سایت متوسط، تک‌تک صفحات `NO DATA` برمی‌گردانند و ۸۰۰ کال هدر می‌رود تا همان عددی را بگیری که `origin` با ۴ کال می‌دهد.

با `--crux pages` پیش‌فرض PageSpeed خودکار به `failed` تغییر می‌کند، چون آن‌وقت حکم PASS/FAIL هر صفحه وجود دارد و می‌شود فقط مردودها را تست کرد.

## ستون `level` — فقط در حالت `--crux pages`

CrUX فقط برای صفحاتی داده دارد که ترافیک کافی داشته باشند. بیشتر صفحات یک سایت متوسط داده‌ی اختصاصی ندارند.

وقتی صفحه‌ای داده نداشته باشد، این ابزار سراغ **سطح دامنه** می‌رود و ستون `level` را روی `origin` می‌گذارد:

- `level = page` → این اعداد مال همین صفحه است
- `level = origin` → این اعداد مال **کل دامنه** است و روی همه‌ی صفحات تکرار می‌شود

اگر این ستون را نبینی، فکر می‌کنی همه‌ی صفحاتت اتفاقاً عدد یکسانی دارند. برای همین سلولش ایتالیک و کم‌رنگ است.

سطح دامنه یک بار به‌ازای هر دامنه×دستگاه پرسیده می‌شود، نه به‌ازای هر URL.

## شیت‌های خروجی

**Summary** — نام سایت، پارامترهای اجرا، شمارش نمرات PageSpeed، و — اگر CrUX اجرا شده باشد — بخش **real users (whole domain)** با اعداد واقعی کاربران دامنه.

**یک شیت به‌ازای هر گروه** — گزارش PageSpeed هر صفحه، مرتب‌شده **از بدترین نمره به بهترین** تا کاری که باید بکنی بالای صفحه باشد. ستون `top opportunities` سه فرصت برتر با تخمین صرفه‌جویی می‌دهد. ستون اول لینک `live test` است که همان صفحه را در pagespeed.web.dev باز می‌کند.

**All** — فقط وقتی بیش از یک گروه داری (مثلاً چند sitemap از یک sitemap index انتخاب کرده باشی). همه‌ی صفحات همه‌ی گروه‌ها را با هم، از بدترین نمره به بهترین، در یک شیت می‌گذارد — تا مجبور نباشی بین چند تب سوییچ کنی تا کل سایت را مرتب یا فیلتر کنی. ستون `source` می‌گوید هر ردیف از کدام sitemap آمده. شیت‌های تک‌تکِ هر گروه هم کنارش می‌مانند.

**Trend** — فقط با `--crux`. تاریخچه‌ی هفتگی LCP، INP و CLS با نمودار متنی، تعداد هفته‌های واقعی، و درصد تغییر.

**CrUX pages** — فقط با `--crux pages` ساخته می‌شود: داده‌ی میدانی تک‌تک صفحات.

### رنگ‌ها

- 🟩 ردیف `PASS` → کل ردیف سبز
- 🟥 ردیف `FAIL` → کل ردیف قرمز، **ولی سلول هر متریکی که استاندارد بوده سبز می‌ماند**
- ⬜ ردیف `NO DATA` → خاکستری
- در شیت PSI رنگ ردیف از نمره‌ی کلی می‌آید ولی هر سلول متریک رنگ خودش را از نمره‌ی همان audit در لایت‌هاوس می‌گیرد

## نکاتی که وقتت را هدر می‌دهند اگر ندانی

**`NO DATA` خطا نیست.** یعنی آن صفحه (و دامنه‌اش) ترافیک کافی برای CrUX نداشته. فقط در حالت `--crux` دیده می‌شود.

**ستون `status` در شیت PageSpeed را نگاه کن.** اگر ردیفی `ERROR` بود، علتش همان‌جا نوشته شده — تایم‌اوت، صفحه‌ی در دسترس نبودن، یا سهمیه‌ی تمام‌شده.

**سهمیه‌ی CrUX ۱۵۰ در دقیقه است و قابل خریدن نیست.** ابزار روی ۱۳۰ محدود می‌کند. هر URL دو کال می‌خورد اگر هر دو دستگاه را بخواهی، و دو برابر می‌شود اگر روند هم روشن باشد.

**نمودار روند عمداً کند است.** هر نقطه میانگین متحرک ۲۸ روزه است و نقطه‌ها هفتگی‌اند، پس دو نقطه‌ی مجاور سه هفته داده‌ی مشترک دارند. اثر یک بهینه‌سازی حدود چهار هفته طول می‌کشد تا کامل بنشیند، و پرش تک‌هفته‌ای اصلاً دیده نمی‌شود.

**ستون `weeks` را نگاه کن.** URL تازه‌ای که سه هفته عمر دارد، برای هفته‌های قبل‌ترش خالی است. بدون این ستون آن خط کوتاه با «افت شدید» اشتباه گرفته می‌شود.

**PSI و CrUX قرار نیست یکی باشند.** نمره‌ی شیت‌های CrUX از داده‌ی میدانی کاربران واقعی می‌آید؛ نمره‌ی شیت PSI از یک اجرای شبیه‌سازی‌شده‌ی آزمایشگاهی. اگر CrUX می‌گوید FAIL ولی PSI می‌گوید GOOD، یعنی صفحه در آزمایشگاه سریع است ولی کاربران واقعی تجربه‌ی بدتری دارند.

**PSI کند است، و دلیلش شبکه نیست.** اندازه‌گیری‌شده روی همین سایت:

```
اتصال TCP + TLS   ~0.7 ثانیه
دانلود پاسخ       ~0.4 ثانیه برای ۶۵۰ کیلوبایت
تا اولین بایت     ۱۴ تا ۲۲ ثانیه   ← تمام زمان اینجاست
```

آن ۱۴ تا ۲۲ ثانیه، مدتی است که گوگل دارد **واقعاً Lighthouse را اجرا می‌کند** قبل از اینکه یک بایت بفرستد. هیچ کاری از دست تو برنمی‌آید جز اینکه چندتا را با هم بفرستی.

**بالا بردن هم‌زمانی کمتر از چیزی که فکر می‌کنی کمک می‌کند.** یک sweep روی ۲۰ URL متمایز در هر سطح:

```
هم‌زمانی   زمان     نرخ          خطا   TTFB سایت خودت
10        110s     11/دقیقه     0     33ms
20         76s     16/دقیقه     1     31ms
40         52s     23/دقیقه     0     73ms
```

چهار برابر کردن هم‌زمانی فقط **دو برابر** سرعت می‌دهد. گوگل خودش صف می‌گذارد، پس سهمیه‌ی ۲۴۰ در دقیقه اصلاً گلوگاه نیست — حتی با ۴۰ تای هم‌زمان به یک‌دهمش هم نمی‌رسیم.

ستون آخر مهم‌تر است: **TTFB خود سایتت از ۳۳ به ۷۳ میلی‌ثانیه رفت.** چهل اجرای هم‌زمان Lighthouse یعنی چهل بار هم‌زمان خزیدن روی سرور خودت. از آنجا به بعد داری نتیجه‌ی لود تستِ خودت را اندازه می‌گیری، نه سرعت واقعی سایت زیر ترافیک عادی.

تخمین زمان با `400` صفحه:

| هم‌زمانی | زمان تقریبی |
| --- | --- |
| ۱۰ (پیش‌فرض) | ~۳۶ دقیقه |
| ۲۰ | ~۲۵ دقیقه |
| ۴۰ | ~۱۸ دقیقه |

پیش‌فرض روی ۱۰ مانده چون بالاتر از ۲۰، عددی که می‌گیری کم‌کم مال سایتِ زیر فشار می‌شود نه سایت عادی. اگر بالاتر بروی ابزار هشدار می‌دهد. `--devices mobile` هم تعداد کال را نصف می‌کند و هیچ عارضه‌ای ندارد.

**نتایج کش‌شده سریع‌اند، ولی کش معمولاً نمی‌خورد.** گوگل تحلیل هر URL را کوتاه‌مدت نگه می‌دارد؛ اگر همان URL را دوباره بپرسی، در کمتر از یک ثانیه جواب می‌گیری. ولی وقتی فهرستت ۴۰۰ آدرس متفاوت است، تقریباً هر کال یک تحلیل تازه است. برای همین اجرای واقعی کند است حتی با اینکه دیده‌ای بعضی جواب‌ها فوری می‌آیند.

**نمره‌ی PageSpeed یک نمونه است، نه یک عدد ثابت.** هر اجرا یک تست زنده روی سرور گوگل است و نتیجه‌اش نوسان دارد. روی یک صفحه‌ی مقاله‌ی وردپرسی، چهار بار پشت‌سرهم گرفتیم:

```
score  FCP     LCP      TBT    CLS     SI
65     3500    9910     146    0.000   3753
65     3500    9910     146    0.000   3753
89     2401    2551     247    0.005   2401
53     3600    10346    180    0.000   3800
```

همان صفحه، همان دقیقه، نمره بین ۵۳ تا ۸۹. TTFB در همه ۳۰ms بود، پس سرور مقصر نیست — عنصر LCP (احتمالاً تصویر hero) گاهی از کش CDN می‌آید و گاهی سرد است.

پس اگر عدد شیت با چیزی که در pagespeed.web.dev می‌بینی فرق داشت، لزوماً باگ نیست. برای تصمیم‌گیری به **الگو** نگاه کن نه به یک عدد: صفحه‌ای که همیشه زیر ۵۰ است واقعاً مشکل دارد؛ صفحه‌ای که بین ۶۰ و ۹۰ می‌رقصد یعنی یک منبع ناپایدار دارد.

**ستون `tested at` زمان خودِ اندازه‌گیری است، نه زمان درخواست ما.** گوگل تحلیل‌ها را کش می‌کند و از هر سروری که جواب بدهد تحویل می‌دهد، پس دو درخواست پشت‌سرهم می‌تواند یک تحلیل چنددقیقه‌ای قبل را برگرداند. این ستون `fetchTime` خود Lighthouse را می‌نویسد تا بفهمی نتیجه چقدر تازه است.

**لینک `live test` عکس فوری نیست.** هر بار بازش کنی تست تازه می‌گیرد، پس عددش با آنچه در شیت ذخیره شده فرق خواهد داشت.

**اگر از ایران اجرا می‌کنی**، بدون پروکسی هر دو API با ۴۰۳ و یک صفحه‌ی HTML رد می‌شوند — نه با خطای JSON. اگر همه‌ی ردیف‌ها یک‌دفعه `NO DATA` شدند، اول مسیر شبکه را چک کن.

```bash
npm test
```

۱۹۷ تست. تست‌های اکسل یک فایل واقعی می‌سازند و دوباره می‌خوانند تا رنگ هر سلول، هایپرلینک‌ها، فریز پنل و اینکه متنِ شروع‌شده با `=` به فرمول تبدیل نشده باشد را بسنجند.
